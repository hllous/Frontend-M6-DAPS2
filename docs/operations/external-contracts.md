## Status and release rule

- `verified-deployed`: exercised against the deployed service or event path, with evidence linked below.
- `verified-source`: confirmed in Backend source or an authoritative integration document at the pinned commit; the deployed path is still unverified.
- `published-unverified`: the other module has published a contract, but the deployed M6-to-module exchange has not been proven.
- `missing`: no authoritative decision or contract exists yet.

Every row states whether it blocks GA. A blocking row is cleared only when its status is `verified-deployed` or the release owner records an explicit accepted exception in #151. This repository review did not call production APIs; no row is marked `verified-deployed` based on this work.

## Current evidence and remaining checks

### M1 authentication and roles

M1 is hosted on Render. On 2026-11-02, `POST /auth/usuario/login` returned 200 for an employee account with an HS256 access token, `sub_type: EMPLEADO`, `rol: RESPONSABLE_AREA`, and a 15-minute lifetime ([Backend #488](https://github.com/hllous/Backend-M6-DAPS2/issues/488), [Frontend #800](https://github.com/hllous/Frontend-M6-DAPS2/issues/800)). The deployed M6 Backend still returns 401 from `GET /me` because its Render `JWT_SECRET` does not match M1's current signing secret. Backend #488 remains open to load the current base64 secret, redeploy, and repeat the login plus `/me` check; until that succeeds, real M1 authentication is not verified end to end.

The next verification must record the active HMAC algorithm and decoded key length against the deployed Backend configuration, confirm that an employee token is accepted by `/me`, and establish the request and renewed-token response shape for `POST /auth/refresh`. The 2/11 login proved a token with HS256 and `sub_type: EMPLEADO` can be issued; it did not prove the deployed Backend accepts that token or settle refresh rotation. The frontend login flow shipped in [PR #802](https://github.com/hllous/Frontend-M6-DAPS2/pull/802); production hardening remains in progress in [#805](https://github.com/hllous/Frontend-M6-DAPS2/issues/805).

M1 has no logout or token-revocation endpoint today: access tokens are not revoked, refresh tokens do not rotate, and logout revokes nothing. The M6 sealed session cookie is stateless, with a 30-minute idle limit and an 8-hour absolute limit; a stolen access token can remain usable for up to 15 minutes. This is an accepted risk recorded in [#795](https://github.com/hllous/Frontend-M6-DAPS2/issues/795) and #805; whether M1 will add a revocation endpoint remains open. The risk does not block GA under the current accepted decision.

An M1 role only bounds which M6 roles can be assigned; Backend computes effective roles on every request. The role-assignment administration surface is tracked in [#797](https://github.com/hllous/Frontend-M6-DAPS2/issues/797) and merged [PR #814](https://github.com/hllous/Frontend-M6-DAPS2/pull/814). The integration monitor and activity log are tracked in [#798](https://github.com/hllous/Frontend-M6-DAPS2/issues/798) and merged [PR #807](https://github.com/hllous/Frontend-M6-DAPS2/pull/807).

### Other external gates

- **M2:** the published ticket-event schemas and `updateTicketStatus` payload are source-checked. The live event exchange and Core's owner/producer registration still need confirmation. M2 has not published the citizen-visible attachment policy or its response projection; do not expose an attachment to citizens by assumption.
- **M3:** M3 published `workOrderScheduled` and `workOrderCompleted` schemas, with `workOrderId` as a technical UUID, optional `workOrderNumber`, and `sourceRequestId` intended to match M6's `requestId`. M3 reports its consumer deployed, but the bilateral `requestId` → `sourceRequestId` test remains pending. Backend's create DTO accepts `address` as an optional string, while its response DTO allows `address: string | null`; the frontend keeps the location required for creation and accepts a null response.
- **M4:** Backend confirms M6's `environmentalViolationDetected` Evidence projection (`evidence[]` uses `{url, mimeType}`). M4's response events document `sourceViolationId` as the M6 `violationId`. The Core/M4 deployed subscription and event exchange still need verification. M4's requested establishment search by address, tax id, or neighborhood remains missing; without it, the frontend cannot reliably obtain the `establishmentId` required to forward a notice.
- **M7:** M7 confirmed `affectedSections` as structured `{street, from, to, direction}` entries, with `direction` in `FORWARD | REVERSE | BOTH`; `closureType` is required on the M6 request. M7 responses use `startDate`/`endDate` and `rejectionReason`, which the Backend exposes as `approvedFrom`/`approvedTo` and `rejectionReason`. Frontend #804 and #806 are merged and display requested and authorized periods separately. Core declaration of `streetClosureEnded` and the coordinated end-to-end exchange remain pending.
- **M9 neighborhoods:** M9 documents 48 real CABA neighborhoods and 15 communes; Backend maps the catalog's neighborhood UUID into M6 Zones. Verify the deployed catalog values and stable neighborhood mapping before release.
- **M9 Core:** M9 reports that Render egress is enabled and Ambiente has an active consumer, but the passive AMQPS test from Render and a coordinated production event exchange remain pending. Verify the exact M7 and M4 subscriptions in the Core before treating their event paths as deployed.
- **Backend #90:** Backend source confirms upload MIME and size validation and metadata cleanup for JPEG, PNG, and WebP. PDFs are stored without metadata cleanup, malware scanning is not implemented, Tier 2 read auditing does not exist, and no export endpoint exists to enforce a server-side allowlist. Verify the deployed upload behavior; resolve or explicitly accept the missing audit and export controls in the release decision.
- **Cancellation:** Backend source confirms `RESCHEDULED → CANCELLED` with a required reason and no replacement date; `IN_PROGRESS → CANCELLED` is rejected. The source contract is closed, and only the deployed Swagger check remains open.
