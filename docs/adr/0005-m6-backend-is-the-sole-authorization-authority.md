# M6 Backend is the sole authorization authority; frontend Capability checks are optimistic

M1 confirmed its application roles (`MESA_ENTRADAS`, `AUDITOR`, `RESPONSABLE_AREA`, `ADMINISTRATIVO`, `PERSONA`) and that it issues the user JWT, but has not published the actual JWT claims contract. Capabilities are therefore resolved from normalized M1 roles/claims through a versioned M6-owned mapping layer; the exact claim extraction remains a hypothesis, and that mapping can drift independently of any actual M1-side permission change. We chose to treat every Capability embedded in the M6 session as strictly optimistic — it shapes the UI only (show/hide, an early client-side gate), never the actual authorization boundary; M6 Backend re-authorizes every request and is final. Capabilities stay frozen for the life of the session (until `jwt.exp`), except that a stale `capabilityPolicyVersion` — meaning M6's own local mapping logic changed, not that M1 changed anything — triggers a local recompute from the already-stored normalized claims, without forcing a new login. That recompute can never see a role change M1 made mid-session, since it works from data already in hand rather than a fresh JWT — the raw JWT stays in the session mainly to keep being forwarded as the Bearer token to M6 Backend, not to re-derive Capabilities from.

A `401` from M6 Backend is treated as more authoritative than the local session state: it invalidates the session immediately — the cookie is cleared, logout is broadcast to every open tab via `BroadcastChannel`, and the tab that received the `401` redirects to `/login` — because the backend knows something the local session doesn't (e.g. revocation). A `403` never invalidates the session: a denial can equally be a stale capability mapping or an unrelated resource, ownership, or state restriction (e.g. a Service already `COMPLETED`), and only a stable business-rule `code` (reusing the `code` field [ADR-0003](0003-hand-written-contract-hypotheses-with-permanent-zod-validation.md) already hypothesizes) lets the frontend tell those apart. Only a `403` whose `code` signals a stale `capabilityPolicyVersion` triggers the local recompute above; a `403` that arrives while the local policy version is already current is treated as a real, final denial, with no retry loop.

**Implementation note (2026-10-01, re-checked against Backend `develop` `30d49ea1d56f735a124ae9260cafefff095e07b6`):** the JWT payload remains the stopgap `{ sub, exp, roles?: string[] }` HS256-against-`JWT_SECRET` strategy from Backend's `adr-002-auth-provisoria.md`, not an M1-issued token. Backend has finished its implementation plan without adding domain `@Roles()` restrictions, so every holder of an accepted JWT can currently call every protected endpoint. That makes the "capabilities are optimistic, the backend is final" posture above *aspirational on the backend side today* — the frontend must gate its demo scenarios, but must not assume a hidden action is also blocked server-side. The current frontend maps selected demo scenarios to capabilities; mapping verified M1 claims remains unimplemented. **M1 stays the intended source of identity and roles**; the HS256 token is a development stopgap, not a second contract to design around. The business-rule `code` field this ADR's `403` handling depends on also does not exist in Backend's shipped `ErrorResponseDto` (see `CONTRACTS.md`), so the stale-`capabilityPolicyVersion` recompute path has no trigger to fire on yet: until a `code` is added, every `403` is treated as a real, final denial.

**Backend alignment (2026-10-01):** Backend formalized the same BFF session boundary, mutually exclusive Office/Field actors, and backend-authoritative security posture in [ADR-005](https://github.com/hllous/Backend-M6-DAPS2/blob/develop/docs/decisiones/adr-005-alineacion-frontend-sesion-y-seguridad.md). The current backend snapshot is `develop` commit `30d49ea1d56f735a124ae9260cafefff095e07b6`; this does not remove the provisional HS256/`JWT_SECRET` limitation recorded above.

**Current implementation status (2026-10-01):** the frontend login chooses a demo scenario; it does not authenticate with M1 or derive the actor from M1 claims. Its BFF checks the selected scenario's capabilities, but those checks are not a trustworthy identity boundary. Backend validates the bearer JWT, but no domain controller currently applies `@Roles()`, so any holder of an accepted JWT can reach protected domain endpoints. Treat capability gating as UX until M1 identity and backend authorization are both integrated.

**Update (2026-10-13):** M1's endpoints document shows login returning `{ user_id, dni, role, auth }` with no token in the body, and adds the `SERVICIO` role (internal system / inter-module calls) to the list above. M1 says it passes a JWT, but it does not appear in the endpoint, so a role cannot be verified yet. None of M1's roles is scoped to an area; Backend proposes that the M1 role only bounds which M6 role can be assigned, with the assignment kept in a local M6 table (hybrid model, Backend #161 and `docs/bloqueantes.md`). Whether the role comes from the M1 JWT or from a token signed by the BFF is undecided and is tracked in [#469](https://github.com/hllous/Frontend-M6-DAPS2/issues/469). The mapping layer above stays a hypothesis.

**Update (2026-10-22, Backend #161 / ADR-008):** the open question is closed. Backend applies `@Roles()` to every route and exposes the effective M6 roles at `GET /me`; the frontend reads them from there (not from the token, not from the demo scenario) and derives its Capabilities from them (`src/lib/m6-roles.ts`). The 403 now carries `code: ROLE_REQUIRED`, so the stale-mapping path above has its trigger: on that code the client re-reads `GET /me` once and recomputes the Capabilities, without retrying the request or ending the session. A 403 without `code` is the `sub_type` denial and a 401 still ends the session. Employees with no M6 role get 403 on reads too; the shell explains it ("Sin rol asignado") instead of showing a generic error. `NOT_ASSIGNED` (Backend #365) will slot in the same way.

**Update (2026-10-30, Backend `374f66e`):** the 2026-10-01 notes above about a stopgap token and no `@Roles()` are superseded. Backend validates M1's published JWT and enforces roles on every write. `NOT_ASSIGNED` has shipped (#365, #394): a Field user acting outside their Crew or assigned inspection gets 403 with that code, which is a real denial, not a stale mapping, so it does not re-read `GET /me`. `GET /me` also returns the caller's `crews`, and the BFF takes Field membership from it (#766). Some rules are stricter than the route-level roles table the frontend mirrors (REMOVAL authorization needs `M6_ADMIN`, Backend #456); those gaps show up as 403 `ROLE_REQUIRED` and the frontend hides those actions (`treeIntervention:authorizeRemoval`, [#770](https://github.com/hllous/Frontend-M6-DAPS2/issues/770)).

Considered Options:
- Treat frontend-embedded capabilities as authoritative and skip re-checking server-side — rejected: any client-side mapping bug or staleness would become an actual authorization bypass, not just a UI glitch.
- Treat every `403` as a capability mismatch and eagerly recompute-and-retry — rejected: most `403`s are unrelated to capabilities at all (resource state, ownership), and blind retries risk request loops.
