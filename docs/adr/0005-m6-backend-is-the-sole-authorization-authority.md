# M6 Backend is the sole authorization authority; frontend Capability checks are optimistic

Capabilities are resolved from M1's identity claims through a frontend-owned mapping layer that is itself a hypothesis until M1 publishes a real claims contract, and that mapping can drift independently of any actual M1-side permission change. We chose to treat every Capability embedded in the M6 session as strictly optimistic — used only to shape the UI (show/hide, an early client-side gate) — never as the actual authorization boundary; M6 Backend re-authorizes every request and is final. Capabilities stay frozen for the life of the session (until `jwt.exp`), except that a stale `capabilityPolicyVersion` — meaning M6's own local mapping logic changed, not that M1 changed anything — triggers a local recompute from the already-stored normalized claims, without forcing a new login; that recompute can never see a role change M1 made mid-session, since it works from data already in hand rather than a fresh JWT. A `401` from M6 Backend is treated as more authoritative than the local session state and invalidates the session immediately (cookie cleared, logout broadcast across tabs), since the backend knows something the local session doesn't (e.g. revocation). A `403` never invalidates the session — a denial can equally be a stale capability mapping or an unrelated resource/ownership/state restriction, and only a stable business-rule `code` (reusing the `code` field [ADR-0003](0003-hand-written-contract-hypotheses-with-permanent-zod-validation.md) already hypothesizes) lets the frontend tell those apart; a `403` that arrives while the local policy version is already current is treated as a real, final denial, with no retry loop.

Considered options:
- Treat frontend-embedded capabilities as authoritative and skip re-checking server-side — rejected: any client-side mapping bug or staleness would become an actual authorization bypass, not just a UI glitch.
- Treat every `403` as a capability mismatch and eagerly recompute-and-retry — rejected: most `403`s are unrelated to capabilities at all (resource state, ownership), and blind retries risk request loops.
