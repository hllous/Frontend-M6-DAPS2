# Hand-written contract hypotheses with permanent Zod validation

At the time of this decision, Backend endpoints didn't exist, so M6's frontend couldn't generate types from a real OpenAPI spec. We chose to hand-write Zod schemas and typed adapters per resource, tracked as hypotheses in `CONTRACTS.md` against Backend's documented API standard, rather than waiting on Backend or building a throwaway ad-hoc client. When Backend publishes its real OpenAPI contract, replacement is scoped to swapping what's *inside* each adapter (the fetch call, and where the schema's shape comes from) — the adapter's public method signatures and inferred TS types stay stable, so the migration never ripples into UI or query-hook code.

The Zod schemas stay on permanently as a runtime-validation layer at the adapter boundary, even after a generated OpenAPI client exists: TypeScript types are a static promise, not a runtime guarantee, and this project can't assume Backend's deployed behavior always matches its own published spec. We picked hand-written-now-plus-permanent-validation over throwaway hypotheses (which would mean redoing the adapter layer, not just its internals, once Backend ships) and over trusting generated types alone (which would drop the "fail fast on contract violation" property the adapter seam exists for).

**Note (2026-09-03):** Backend has since finished all seven phases of its plan — 130 routes, mirrored in `docs/backend-context/api/endpoints.md` — and it serves a live Swagger document at `/api/docs`. This does **not** reverse the decision. There is still no OpenAPI artifact published as a versioned contract to generate from, and the Zod layer was always meant to outlive one. What changes is only where `CONTRACTS.md` gets its shapes: read off the mirror and the backend source instead of inferred from the API standard. Generating a client from the live Swagger document remains an option to revisit, and would replace adapter internals exactly as this ADR anticipated.
