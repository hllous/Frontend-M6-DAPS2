# Hand-written contract hypotheses with permanent Zod validation

At the time of this decision, Backend endpoints didn't exist, so M6's frontend couldn't generate types from an OpenAPI contract. We chose to hand-write Zod schemas and typed adapters per resource, initially tracked as hypotheses in `CONTRACTS.md`, rather than wait on Backend or build a throwaway ad-hoc client. As Backend's contract becomes more complete, replacement stays scoped to the adapter internals (the fetch call and the source of the schema); view-level types and behavior should remain stable where the contract allows.

The Zod schemas stay on permanently as a runtime-validation layer at the adapter boundary, even after a generated OpenAPI client exists: TypeScript types are a static promise, not a runtime guarantee, and this project can't assume Backend's deployed behavior always matches its own published spec. We picked hand-written-now-plus-permanent-validation over throwaway hypotheses (which would mean redoing the adapter layer, not just its internals, once Backend ships) and over trusting generated types alone (which would drop the "fail fast on contract violation" property the adapter seam exists for).

**Status note (2026-09-30):** Backend has completed its seven implementation phases. The current mirror is from `develop` commit `eda505f`, with 130 routes across 23 tags; Swagger is served at `/api/docs`. This does **not** reverse the decision. The repository still has no versioned OpenAPI artifact to generate a client from, and the Zod layer was meant to outlive code generation. `CONTRACTS.md` now reads confirmed shapes from the mirror and implementation, while retaining explicit hypotheses for undocumented shapes and integrations. Revisit client generation only when a stable, versioned schema is available.
