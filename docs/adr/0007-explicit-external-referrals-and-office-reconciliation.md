# Explicit external referrals and Office reconciliation

The M6 frontend tracks two requests whose decisions belong to other modules: `RepairRequest` is referred to M3, and `StreetClosureRequest` is referred to M7. Their external responses arrive asynchronously, while the backend also exposes transition endpoints for manual operation and for environments without the event bus. A referral can therefore be pending, duplicated, stale, submitted with an uncertain result, or updated after its source Service changes ([#66](https://github.com/hllous/Frontend-M6-DAPS2/issues/66)).

We chose to create referrals explicitly from their source context rather than infer them. A `RepairRequest` starts from a `Service` or `EnvironmentalInspection`; a `StreetClosureRequest` starts from a `Service` or an authorized `TreeIntervention`. Container public-works notifications remain on the separate `containerDamaged` path. `Office` can create and view all referrals; `Field` can create a repair referral only from assigned work and can view only referrals attached to assigned Services; street-closure creation remains Office-only. The source reference stays authoritative — the interface shows a navigable context summary, never a duplicated second authoritative record.

`publicSafetyRisk` is captured explicitly and independently from repair `severity`. A street-closure request requires at least one structured `affectedSection` and captures the requested window when the source has scheduled work. Evidence, when present, remains attached to the source resource, because referral entities are not valid Evidence owners.

External event transitions are read-only in normal product use. A pending `StreetClosureRequest` is a dependency that prevents its Service from starting; an approved response permits execution, a rejected response requires Office to choose rescheduling or cancellation, and an ended response releases the dependency. A ROUTE Service is blocked as a whole, because the referral points to the Service, not to an individual zone. Manual transition endpoints are exposed only as explicit Office-only recovery, requiring review, confirmation, and the external identifier where applicable — M6 never invents an M3/M7 decision.

Anomalies stay out of the domain state machine: stale is an operational warning, not a new state; duplicate candidates require human review; an uncertain submission is reconciled before retry; and out-of-order or uncorrelated external responses never reopen or overwrite a Service. Source changes preserve the original referral and require explicit reconciliation.

This keeps M6's product state subordinate to M3/M7's external decisions and avoids unsafe automatic retries, merges, or Service reopening. Office receives explicit reconciliation work when integrations are late or ambiguous. The frontend must present source context, timestamps, external identifiers, and the difference between an unsent referral (submission failed before a record was created) and a created-but-pending one. Correlation and machine-readable error details remain backend contract concerns; the frontend must not classify ambiguous free-text errors as duplicates.

No alternatives were recorded in issue #66's resolution.
